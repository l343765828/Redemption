# 双轨制左右区业绩（1L/2L）计算逻辑深度解析（修正版）

**校正声明：** 本版依据 `CALC_PV.sql` 的真实执行轨迹修正而成。核心结论是：真正完成"左右区业绩求和"的，是 **MID4 明细表生成之后的那一步集中 `GROUP BY` 聚合**；WHILE 循环与递归 CTE 只负责"逐个源用户、把个人消费展开成贡献明细"。

需要澄清两种容易对立起来的说法其实并不矛盾：

- **"逐用户独立贡献"** 描述的是数据生成阶段——每个源用户各自把自己的 `PV_PCS` 贡献给它的所有祖先，**各用户之间无先后依赖**（这正是后文并行化改造的依据）。
- **"集中聚合才是计算核心"** 描述的是结果产出阶段——最终的 `PV_1L / PV_2L` 是对 MID4 全表做 `GROUP BY` 求和得到的，而不是在递归里"算完一棵树"得到的。

后者是对前者的**补全**，不是推翻。本文同时摒弃了"按网络层级滚雪球"这一最常见的误读（系统确有"层数"概念，但它由独立过程 `CALC_BE_NET` 维护在 `TOP_DEEP` 字段，`CALC_PV` 计算 1L/2L 时并不使用层数）。

## 一、业务背景与快照公式（What）

根据《奖金制度.pdf》，Team B（团队奖金）在业务规则上采用典型的双轨制（安置网）对碰逻辑，会员级别不同，对应的对碰比例分为 0%、10%、15%、20% 等。

**技术边界需明确：** `CALC_PV.sql` 仅负责计算左右区业绩**基数**，并不负责"对碰、封顶、扣减、结余更新、奖金池比例分摊"等 Team Bonus 完整发奖逻辑。它的职责，是为下游发奖明确每个人当期的左区（1L）与右区（2L）总业绩。

落库到 `AR_PERF_MONTH`（月度快照表）供下游使用的核心公式：

```
本期左区总业绩 (TOTAL_1L) = 本期左区新增 (PV_1L) + 上期左区结余 (PRE_SURPLUS_1L)
本期右区总业绩 (TOTAL_2L) = 本期右区新增 (PV_2L) + 上期右区结余 (PRE_SURPLUS_2L)
```

核心技术难点在于：本期新增的 `PV_1L` 与 `PV_2L`，到底是如何在网体中精准生成的？

## 二、真实的底层计算引擎：双图流水线 + 集中聚合（How）

`CALC_PV.sql` 的机制不是层级推演，也不是"每个用户独立算完一棵树"，而是一条"**逐行明细生成 → 集中聚合**"的流水线。

### 1. 不同用途的双图结构，在同一流水线中被调用

脚本针对不同业务目标，调用了两套完全不同的网络拓扑，且存在**重要的不对称性**：

- **树 A：推荐网（`AR_USER_RELATION_NEW`）** → MID2 / MID3 → 生成小组业绩的基础原料（如 `PV_PSS`）。
  *注：`PV_PSS` 在 MID2 的递归锚点 `WHERE A.USER_ID = VV_USER_ID` 处把用户自己也计了进去，因此 **`PV_PSS` 含本人自身消费**；且它只是推荐网下属的原始累加和，**不等于**带"满 1000BV 封顶 / 虚拟宽度 / PE 以上重新紧缩网络"等规则的最终判定用 PGS——那些规则由其他过程处理。*

- **树 B：安置网（`AR_USER_NETWORK_NEW`）** → MID4 / MID5 → 计算双轨左右区业绩（`PV_1L / PV_2L`）。
  *注：MID4 的收款人永远是路径节点的"父"，所以源用户自己的消费不进自己的左右区，**1L/2L 不含本人自身消费**，符合双轨制"自己业绩不算在自己腿上"的常识。*

> 补充：系统确实维护"网络层数"，但那是 `CALC_BE_NET` 过程做的事——它自上而下（根节点 `PARENT_UID='0'` 记 0，每层 +1）把层数写进两张网各自的 `TOP_DEEP` 字段。`CALC_PV` 全程**不引用 `TOP_DEEP`**，也不依赖 `CALC_BE_NET` 先跑；二者解耦。这也反证了 `CALC_PV` 中声明的 `VV_MAX_LAYER` 是**未被使用的废弃变量**。

### 2. 梳理"源用户池"

计算起点是从 `AR_PERF_ORDER` 按 `USER_ID` 聚合，将个人消费 `SUM(PV)` 汇总到 `AR_CALC_PV_MID1`。

*注：当前 SQL 文本未显式 `HAVING SUM(PV) > 0`，且周期过滤 `WHERE T.PERIOD_NUM = IV_PERIOD_NUM` 可能已被注释。若 `AR_PERF_ORDER` 已由上游限定为当期有效订单，则 MID1 可视为当期个人消费池。*

### 3. WHILE 循环 = 调度器（非计算核心，更非层级循环）

WHILE 不按网络层数循环，而是以 MID1 的"用户 PV 汇总记录"为粒度逐条触发。`VV_COUNT` 来自"用户数 − 1"，与层数无关：

```sql
SELECT COUNT(1) - 1 INTO VV_COUNT FROM AR_CALC_PV_MID1;
WHILE VV_COUNT >= 0 DO
  -- 用 LIMIT 逐条拉起一个源用户
  SELECT T.USER_ID, T.PV_PCS INTO VV_USER_ID, VV_PV_PCS
    FROM AR_CALC_PV_MID1 T LIMIT VV_COUNT, 1;
  ... 触发单用户路径展开 ...
  SET VV_COUNT = VV_COUNT - 1;
END WHILE;
```

### 4. 路径展开与明细生成（写入 MID4 事实表）

对每个被取出的源用户（设为 B，消费 100 PV）：

- **递归找祖先：** 用 `WITH RECURSIVE` 顺着安置网从 B 向上展开到顶点，取出 B 路径上的所有直系长辈。
- **生成明细：** B 不在这里独立算完一棵树，而是把自己的 100 PV（作为 `SOURCE_PV_PCS`）写成 MID4 中**每位长辈名下的一条明细记录**。
- **绑定区位（`RELATIVE_LOCATION`）：** 判定左右区时，看的是"源用户路径中、该祖先的直接下级节点"挂在该祖先哪条腿上。即对路径里 `PARENT_UID = A` 的那一行，取它相对 A 的 `RELATIVE_LOCATION` 作为这笔明细在 A 名下的左右标识：`=1` 记 A 的左区、`=2` 记 A 的右区。
  *（举例：B 在 C 左腿、C 在 A 右腿 → 给 C 记账用 B 的腿，B 进 C 的 1L；给 A 记账用 C 的腿，B 进 A 的 2L。结果正好等于"B 落在该祖先的哪棵子树里"。）*

### 5. 集中聚合，生成当期新增（核心计算发生在这一步）

真正执行数学意义"左右区求和"的，**不是上面的递归或循环，而是 MID4 明细全部写完之后的集中聚合**。系统对 MID4 做 `GROUP BY`：

```sql
INSERT INTO AR_CALC_PV_MID5
SELECT T.USER_ID,
  IFNULL(SUM(CASE WHEN T.RELATIVE_LOCATION = 1 THEN T.SOURCE_PV_PCS END), 0) AS PV_1L,
  IFNULL(SUM(CASE WHEN T.RELATIVE_LOCATION = 2 THEN T.SOURCE_PV_PCS END), 0) AS PV_2L
FROM AR_CALC_PV_MID4 T
GROUP BY T.USER_ID;
```

正是这一步，才诞生了每个人当期的新增 `PV_1L / PV_2L`。**递归 CTE 只是用来生成 MID4 的明细数据，不是最终的左右区计算逻辑。**

## 三、生成最终快照与活跃状态回写

MID5 产出当期新增后，进入组装与落库：

1. **全集组装（MID7）：** 通过 **UNION** 汇总当月所有有业绩的节点，得到完整人员名单。注意这是**四路并集**：MID1（个人消费）/ MID3（团队）/ MID5（市场）/ **MID6（存货商）**——存货商这一路常被"等"字省略，但它确实在并集里。

2. **合并结余（MID8）：** 在 MID8 中 `LEFT JOIN AR_USER_PERF`（业绩主表）取上期未对碰完的结余，并在此处**真实执行"新增 + 结余"的加法**，得出 `TOTAL_1L / TOTAL_2L`。（即 TOTAL 的加法落在 MID8，而非 MID5。）

3. **写入快照（`AR_PERF_MONTH`）：** 将各项 PV 指标连同活跃状态插入快照表。

   **⚠ 关键修正——快照里的活跃状态不是"初步判定"：** 写入快照那一刻，`IS_ACTIVE` 字段就已经是

   ```sql
   CASE WHEN T2.USER_ID IS NOT NULL THEN 1 ELSE T.IS_ACTIVE END
   --  T2 = (SELECT USER_ID FROM AR_PERF_ACTIVE GROUP BY USER_ID)
   --  T.IS_ACTIVE = (IFNULL(PV_PCS,0) >= VV_IS_ACTIVE ? 1 : 0)
   ```

   也就是说，**AR_PERF_ACTIVE 名单的强制活跃，在写快照的当下就已经并入**。快照里的 `IS_ACTIVE` 含义是"在 AR_PERF_ACTIVE 名单中 **OR** PV_PCS ≥ 阈值"，而非纯 PV 判定。直接影响下游：一个 PV 不足阈值、但在 AR_PERF_ACTIVE 名单里的人，**在快照里照样活跃、照样有 TB 资格**。

4. **状态回写主表（与快照解耦）：** 写完快照后，脚本并未结束，还有两条 UPDATE 把活跃状态同步回**主表 `AR_USER_PERF`**：

   ```sql
   -- ① 把快照算好的 IS_ACTIVE 同步回主表（只覆盖进了快照、即出现在 MID7 的人）
   UPDATE AR_USER_PERF T INNER JOIN AR_PERF_MONTH T1 ON T.USER_ID = T1.USER_ID
      SET T.IS_ACTIVE = T1.IS_ACTIVE;
   -- ② AR_PERF_ACTIVE 名单里的人，在主表强制刷 1
   UPDATE AR_USER_PERF T INNER JOIN AR_PERF_ACTIVE T1 ON T.USER_ID = T1.USER_ID
      SET T.IS_ACTIVE = 1;
   ```

   UPDATE ② 并非与 ① 重复：一个在 AR_PERF_ACTIVE 名单、但当月既无消费也无团队/市场/存货商业绩的人，根本不会进 MID7→不在快照→① 碰不到他，必须靠 ② 在主表把他补成活跃。

至此 `CALC_PV.sql` 的任务结束。`AR_PERF_MONTH` 作为快照，是下游 Team Bonus 计算的输入；下游据其中的基数执行对碰与发奖。

## 四、架构重构启示（To-Be 改造建议，致开发团队）

> 本节为**改造建议**，描述目标态（To-Be），非对现有代码（As-Is）的描述。

现有机制虽然在单机 MySQL 存储过程里表现为低效的逐行 WHILE 调度，但它为分布式重构指明了清晰路线：

- WHILE 的作用仅是**调度器**，向 MID4 写入的各笔明细**相互之间毫无依赖**；
- 因此迁移到 Spark / Dask 等引擎时，可直接摒弃逐行调度循环，改用扁平化的**闭包表（Closure Table）**做大规模 JOIN，再以 MapReduce 思路执行"MID4 → MID5"式的全盘分布式 `GROUP BY` 聚合。

这种"明细事实生成 + 集中聚合"的数据模型天生适合并行化改造。
