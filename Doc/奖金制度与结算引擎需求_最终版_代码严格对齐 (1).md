> **本版目的**：以 `UserStatsService.py`、`HonorLevelGPUService_fixed.py`、`HonorLevelHighGPUService.py`、`LeadershipBonusGPUService_fixed__1_.py`、`UserStats.py`、`奖金制度.pdf` 为事实来源，对奖金制度中 Elite / Honor / Leadership Bonus 三部分做代码严格对齐，并明确区分：
>
> - PDF 业务规则
> - 当前代码实现
> - PDF 与代码之间的缺口 / 冲突
>
> 本版可作为当前阶段的**最终审校稿**。

## 0. 全局架构与服务职责

奖金体系由 **4 个**独立服务协作，数据通过 Redis 或 GPU 快照传递，各服务职责如下：

| # | 服务 | 职责 | 数据介质 | 触发方式 |
|---|------|------|----------|----------|
| 1 | `UserStatsService` | Elite 实体级别（rank 0/1/2/3）、`qualified_legs`、`virtual_width`、`gpv`、`contrib` 实时维护 | Redis | 事件驱动 |
| 2 | `HonorLevelGPUService` | 当月 SE 深度/宽度、`ori_honor_calc_id` / `bonus_honor_calc_id` / `last_honor_calc_id`、GPV 拆分、LB_PV 归集 | cuDF / GPU | 月度全量快照 |
| 3 | `HonorLevelHighGPUService` | 历史最高奖衔滚动判定（只升不降） | cuDF / GPU | 月度，消费当月奖衔 + 历史记录 |
| 4 | `LeadershipBonusGPUService` | 大区奖金池拨出、逐层向上递归、双重拦截、落 6 张结果表 | cuDF / GPU | 月度，消费 Honor 快照 |

**关键事实：**

- `HonorLevelGPUService` 不重算 Elite，只消费 `rank → last_elite_calc_id` 映射：`0 → 0`, `1 → 10`, `2 → 20`, `3 → 30`。
- `LeadershipBonusGPUService` 若传入 `df_honor_high`，仅用于覆盖展示字段 `last_honor_calc_id` / `last_honor_lv`，**不参与** Leadership Bonus 拦截。

## 1. 核心业务数据定义

### 1.1 BV / PV / GPV

| 字段 | 含义 | 归属 |
|------|------|------|
| BV | 业绩单位，按产品固定，保留 2 位小数 | PDF 规范 |
| PV / PS_BV | 个人消费 BV | 代码字段 `UserStats.pv` |
| GPV | 个人小组业绩 | 代码字段 `UserStats.gpv` |

### 1.2 两种"活跃"的严格区分

| 名称 | 字段位置 | 定义 | 归属 |
|------|----------|------|------|
| 会员活跃 | `AR_USER.is_active` | PDF：月个人消费 ≥ 30 BV | PDF 规范，**当前代码未计算** |
| SE 活跃 | Honor 内部派生 | `last_elite_calc_id == 30` AND `lb_pv > 0` | 代码实现 |

**说明：**

- `UserStats` 模型字段只有 `id / user_id / pv / gpv / contrib / is_elite / virtual_width / rank / qualified_legs`，**没有 `is_active` 字段**。
- 当前 `LeadershipBonusGPUService` 中，`is_active` 仅透传到输出表，**不参与金额拦截**。

### 1.3 虚拟宽度（Virtual Width）

- **触发条件**：`gpv >= 2000`
- **计算**：`virtual_width = gpv // 1000`
- **作用范围**：仅在 Elite 晋级判定中使用，Honor 的深度 / 宽度递归**不使用**虚拟宽度。

### 1.4 GPV 拆分为 LB_PV

`HonorLevelGPUService` 内部动态推导：

```
gpv >= 2000         ->  gpv_real = 1000, gpv_unreal = gpv - 1000
1000 <= gpv < 2000  ->  gpv_real = gpv,  gpv_unreal = 0
gpv < 1000          ->  gpv_real = 0,    gpv_unreal = 0
```

该拆分**每次全量重算，不依赖 Redis 缓存**。

### 1.5 LB_PV 向 SE 的归集路由（防抱团）

| 业绩类型 | 去向 |
|----------|------|
| `gpv_unreal` | 无条件给最近上级 SE（`parent_se_id`） |
| `gpv_real` | 若 `parent_uid == parent_se_id`，越级给 `grandpa_se_id`；否则给 `parent_se_id` |

**最终：**

```
lb_pv = lb_unreal + lb_real
```

这套逻辑在 `HonorLevelGPUService` 和 `LeadershipBonusGPUService` 中口径一致。

## 2. Elite 级别判定（`UserStatsService`）

**常量：**

```
ELITE_MARK = 1000
VIRTUAL_MARK = 2000
```

**规则：**

- **Elite（rank=1）**：`gpv >= 1000`
- **Pro Elite（rank=2）**：
  - A：自身是 Elite，且 `len(qualified_legs) + virtual_width >= 1`
  - B：自身不是 Elite，但 `len(qualified_legs) + virtual_width >= 2`
- **Super Elite（rank=3）**：`len(qualified_legs) + virtual_width >= 3`

**合格腿加入条件：**

某条直推下级 `leg` 合格，当且仅当：

- `leg.rank >= 1`，**或**
- `len(leg.qualified_legs) + leg.virtual_width > 0`

**向上冒泡停止条件：**

- `delta_update == 0`
- **且**该上级 `(is_elite, rank, len(qualified_legs))` 三元组未变化

I/O 使用 Redis Pipeline 批量写入。

## 3. Honor Level 奖衔规则（`HonorLevelGPUService`）

### 3.1 前置条件

- `last_elite_calc_id` 由 rank×10 映射而来
- 非 SE（`last_elite_calc_id < 30`）不参与 Honor 评定
- 参与深度 / 宽度递归还必须满足 SE 活跃：`lb_pv > 0`

### 3.2 SE 网络（两张边集）

| 边集 | 过滤条件 | 用途 |
|------|----------|------|
| `df_se_edges_all` | `last_elite_calc_id == 30` 且 `parent_se_id != 0` | 宽度计算 |
| `df_se_edges_active` | 上述边集且 `dst` 为活跃 SE | 深度计算 |

### 3.3 深度与宽度字段语义

| 字段 | 含义 |
|------|------|
| `legs_max_calc_id` | 最深 SE 代数 × 10，种子为 10，每跳 +10，**本身不封顶** |
| `raw_longest_se_num` | 最长 SE 链长度（含自己） |
| `se_num_excluding_self` | `max(raw_longest_se_num - 1, 0)` |
| `honor70_legs` | 分支最大深度 `>= 1` 的分支数 |
| `honor80_legs` | 分支最大深度 `>= 2` 的分支数 |
| `honor90_legs` | 分支最大深度 `>= 3` 的分支数 |

**特别说明：**

`legs_max_calc_id` 不是"封顶 60"的字段。它会继续增长到 70 / 80 / 90 甚至更高；只有在回落到 10~60 档公式时才做 `min(legs, 60)`。

### 3.4 当月奖衔判定

```
IF  legs_max_calc_id >= 90 AND honor90_legs >= 3  ->  ori = 90
ELIF legs_max_calc_id >= 80 AND honor80_legs >= 3  ->  ori = 80
ELIF legs_max_calc_id >= 70 AND honor70_legs >= 3  ->  ori = 70
ELSE                                               ->  ori = (min(legs_max_calc_id, 60) // 10) * 10
```

**等级对应关系：**

- `10 / 20 / 30` = Director / 2S Director / 3S Director
- `40 / 50 / 60` = Diamond / 2S Diamond / 3S Diamond
- `70 / 80 / 90` = Crown / 2S Crown / 3S Crown

非活跃 SE 一律：`ori_honor_calc_id = 0`

### 3.5 三层等级字段

| 字段 | 公式 | 语义 |
|------|------|------|
| `ori_honor_calc_id` | 当月深度 / 宽度评定结果 | **业绩等级** |
| `limit_honor_calc_id` | 当前快照构造里默认写 90 | **会员资格上限** |
| `bonus_honor_calc_id` | `min(ori, limit)` | **拿钱等级** |
| `last_honor_calc_id` | `min(bonus, se_num_excluding_self * 10)` | **当月最终展示等级** |

**注意：**

PDF 里"D / SD / GD / PD 对应不同奖衔上限"的规则在当前代码中**没有真正实现**；当前 `HonorLevelGPUService.build_snapshots_from_redis` 直接把 `limit_honor_calc_id` 硬编码为 90。

### 3.6 历史最高奖衔（`HonorLevelHighGPUService`）

这一段需要特别说明：**PDF 与代码口径并不完全一致，而且 PDF 第 3 页内部本身就有冲突**。

#### 3.6.1 PDF 第 3 页存在两套口径

PDF 同时写了：

**通用滚动规则：**
> "取得各级奖衔连续 3 个月，或 6 个月内有 4 个月符合，两者取最高，为最高奖衔。只升不降。"

**特殊规则：**
> "1st_Director - 1st_Crown 直接取最高；达到 2 star crown 需要 12 个月内达到两次；3 star crown 需要 3 次。"

#### 3.6.2 当前代码实际实现

当前 `HonorLevelHighGPUService.py` 实现的是下面这套规则：

| 阶段 | 目标等级 | 判定逻辑 |
|------|----------|----------|
| 阶段 2 | 10 ~ 70 | `cur_calc < 70` 且 `last_calc > cur_calc`，则升级到 `min(last_calc, 70)` |
| 阶段 3 | 80 | 12 周期窗口内，`last_honor_calc_id >= 80` 的次数 `>= 2` |
| 阶段 4 | 90 | 12 周期窗口内，`last_honor_calc_id == 90` 的次数 `>= 3` |

**注意阶段 3 / 4 的等号差异**：80 级用 `>= 80`（即 80 和 90 都算一次），90 级用 `== 90`（严格等于）。

**PUSH 补录过滤条件：**

```
(iv_period_num - 11) <= period_num <= (iv_period_num - 1)
AND last_honor_calc_id >= 80
```

**另外**：`iv_calc_month` 参数虽然存在于函数签名中，但在判定逻辑里**实际未被使用**，仅透传到输出表的 `calc_month` 字段。这在日后引入 PDF 通用规则（"连续 3 个月"或"6 个月内 4 次"）时，可作为预留入口；若最终确认以特殊规则为准，建议在后续重构时清理该参数或加注释说明用途。

#### 3.6.3 本版最终结论

因此，本版不再写成"代码未实现 PDF 通用规则"这么简单，而是明确为：

- **PDF 第 3 页内部存在冲突口径**
- **当前代码采用了后半段特殊规则**
- **业务上必须确认最终以哪套为准**
  - 若以后半段特殊规则为准，应修订 PDF
  - 若以前半段通用滚动规则为准，应修改代码

## 4. Leadership Bonus 结算（`LeadershipBonusGPUService`）

### 4.1 输入契约

| 参数 | 来源 | 关键字段 |
|------|------|----------|
| `df_users` | AR_USER | `user_id, user_name, real_name, country_id, is_active` |
| `df_honor_snapshot` | `HonorLevelGPUService.df_f` | 覆盖 Honor 输出字段 |
| `df_perf_month` | AR_USER_PERF | `period_num, country_id, pv_pcs` |
| `df_honor_levels` | AR_HONOR_LEVEL | `calc_id, honor_lv` |
| `df_config` | AR_CONFIG（`type='bonus'`） | `leadershipRate10..90` + `CountryXX` |
| `df_honor_high`（可选） | `HonorLevelHighGPUService.df_result` | 仅覆盖展示字段 |

### 4.2 配置驱动的大区

代码**不是**把 MY/SG/BN、TW/HK 写死，而是通过配置表中 `CountryXX -> region_default_id` 映射决定：

```python
df_region_cfg = df_config_bonus[df_config_bonus["config_name"].str.startswith("Country")]
df_region_cfg["source_country_id"] = df_region_cfg["config_name"].str.replace("Country", "")
df_region_cfg["region_default_id"] = df_region_cfg["value"]
```

所以：

- PDF 中 MY/SG/BN、TW/HK 是**业务举例**
- 代码层面是**配置驱动**，不是硬编码

### 4.3 奖金池配置（9 代 × 3 档）

| 代数 | calc_id | 比例 | 配置键 |
|------|---------|------|--------|
| 第 1–3 代 | 10 / 20 / 30 | 4.5% | `leadershipRate10/20/30` |
| 第 4–6 代 | 40 / 50 / 60 | 3.6% | `leadershipRate40/50/60` |
| 第 7–9 代 | 70 / 80 / 90 | 1.8% | `leadershipRate70/80/90` |

### 4.4 向上递归（全局 MID5_1）

- 每个活跃 SE 自己就是第 1 层，`layer_calc_id = 10`
- 只在"活跃 SE → 活跃父 SE"链上递归
- 每跳一层 `layer_calc_id += 10`
- 最终按 `(user_id, layer_calc_id, country_id)` 聚合 `seed_lb_pv → lb_pv`

### 4.5 双重拦截

**第 1 道拦截**：`layer_calc_id <= ori_honor_calc_id`
- 作用：决定该笔业绩是否进入该层奖池**分母**
- 对应 PDF：**旁线级别不够，不计算**

**第 2 道拦截**：`layer_calc_id <= bonus_honor_calc_id`
- 作用：决定这笔理论奖金是否**真正发放**
- 对应 PDF：**会员级别不够，算出来不发**

这是当前代码里非常关键的一点，且是两道不同性质的拦截。

### 4.6 单价 `lb_rate` 计算

对每个 `(calc_country_id, layer_calc_id)`：

```
honor_bonus = TRUNCATE(total_pv * honor_rate, 6)
lb_rate     = TRUNCATE(honor_bonus / total_lb_pv, 6)
row_bonus   = TRUNCATE(lb_pv * lb_rate, 2)
```

`total_pv` 来自 `df_perf_month` 按大区聚合。

### 4.7 同区还原（DETAIL_COUNTRY 层）

```
if calc_country_id == u_region:
    bonus_country_id = user_country
else:
    bonus_country_id = calc_country_id
```

### 4.8 溯源表的 bonus_country_id 三分支

```
if 下单国无大区配置:
    bonus_country_id = source_country_id
elif 下单大区 == 拿奖人大区:
    bonus_country_id = b_country_id
else:
    bonus_country_id = rc1_reg
```

### 4.9 精度处理

| 字段 | 截断策略 | 位置 |
|------|----------|------|
| `honor_rate * total_pv -> honor_bonus` | 截断 6 位 | `df_rate` |
| `honor_bonus / total_lb_pv -> lb_rate` | 截断 6 位 | `df_rate` |
| `lb_pv * lb_rate -> row_bonus` | 截断 2 位 | `df_detail1` |
| `bonus_lb`, `valid_bonus_lb` | 截断 2 位 | `df_bonus_country` |
| `df_global_detail.lb_rate` | **未截断** | 全局明细层 |

`_truncate_gpu` 使用 `cp.nextafter(..., cp.inf)` 后再 `cp.trunc`，用于修复浮点下沉误差。

## 7. PDF 规范与代码实现的缺口清单（最终版）

当前需要重点关注的缺口共有 **4 项**：

### 缺口 #1：会员活跃度（30 BV / 月）未落地

- **PDF**：月个人消费累计 ≥ 30 BV 视为活跃；不活跃算出来不发
- **代码**：
  - `UserStats` 模型无 `is_active`
  - `HonorLevelGPUService.build_snapshots_from_redis` 把 `is_active` 硬编码为 1
  - `LeadershipBonusGPUService` 中 `is_active` 只透传不拦截

**结论**：当前代码未真正落地"活跃发奖限制"。

### 缺口 #2：`limit_honor_calc_id`（会员资格上限）未落地

- **PDF**：D / SD / GD / PD 对应不同奖衔上限
- **代码**：当前统一硬编码为 90

**结论**：第 2 道 Leadership 拦截虽然存在，但会员资格上限实际未生效。

### 缺口 #3：历史最高奖衔规则存在"PDF / 代码口径冲突"

这条是本版的关键结论。

- PDF 第 3 页同时写了：
  - 通用滚动规则：连续 3 个月 / 6 个月 4 次
  - 特殊规则：1st_Director ~ 1st_Crown 直接取最高；2S Crown 12 个月 2 次；3S Crown 3 次
- 代码实际实现的是**后者**

**最终结论**：

- 不是单纯"代码少实现了一段"
- 而是 **PDF 自身口径冲突**，代码选用了其中特殊规则版本
- 业务上需确认**最终以哪套为准**

### 缺口 #4：全球汇总层 `lb_rate` 未做 6 位截断

`AR_CALC_BE_LB_DETAIL.lb_rate` 没有再次做 `TRUNCATE(..., 6)`，如对账系统要求严格一致，可能出现尾差。

## 8. 结论

### 8.1 可以直接认定为"代码事实"的部分

以下内容已经可以作为当前代码口径的**稳定结论**：

- Elite / Pro Elite / Super Elite 的晋级规则
- GPV 拆分 `gpv_real` / `gpv_unreal`
- LB_PV 的最近 SE / 越级 SE 归集规则
- Honor 当月 10~90 的判定逻辑
- Leadership Bonus 的 9 代递归与两道拦截
- Leadership Bonus 实际返回 6 张表
- 大区规则为配置驱动，不是硬编码

### 8.2 当前不能直接写成"已实现"的部分

以下内容**不能**在需求文档里写成"代码已实现"：

- 会员活跃度 30 BV / 月发奖限制
- 会员类型对应 `limit_honor_calc_id`
- PDF 第 3 页的通用滚动规则
- 全球汇总层 `lb_rate` 统一 6 位截断
