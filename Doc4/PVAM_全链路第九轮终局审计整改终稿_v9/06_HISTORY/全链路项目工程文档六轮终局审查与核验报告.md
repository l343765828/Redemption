### 2.4 F5-06 未批准前置提交复现

合成历史为 `base → arbitrary_commit → WORK-02`，其中 `arbitrary_commit` 只新增不在模拟 WORK-01 scope 中的 `outside.txt`；provenance 自行把该提交标成 `WORK-PVAM-01`。实测：

```text
PARENT_PROVENANCE_PASS WORK-PVAM-02 parent=<arbitrary_commit> direct=1 closure=1
PROVENANCE_LABEL_SPOOF_ACCEPTED outside.txt_as_WORK-PVAM-01
exit=0
```

校验器只执行 Git 对象与自报顺序对账：

```python
work_id = entry["work_id"]
commit_sha = git(repo, "rev-parse", f"{commit_value}^{{commit}}")
tree_sha = git(repo, "rev-parse", f"{tree_value}^{{tree}}")
history = git(repo, "rev-list", "--first-parent", "--reverse", f"{base_sha}..{parent_commit_sha}")
if history != expected_history:
    fail(...)
```

没有受信任的 `work_id→approved commit/tree/evidence SHA` 登记，也没有对 included prerequisite commit 逐项运行其自身 scope/patch/provenance 门禁。故该模型能拦截“额外未登记提交”，却不能拦截“把任意提交登记成允许 WORK”的夹带。

## 3. 审核总结论

### 【REJECTED】

本套件尚未达到“文档治理 APPROVED / APPROVED_FOR_CONSTRUCTION（可下发编码施工）”的正式准入标准，不能从第五轮 `REJECTED` 升格。

### 3.1 阻断依据

1. **F5-01 未彻底关闭。** 五层解析已显著加强，普通孤儿/删边能被阻断；但重复受控元数据与重复非核心定义形成可复现影子边/影子状态，校验器仍给出错误 PASS。
2. **F5-06 未彻底关闭。** PARENT_PROVENANCE v2 的 commit/tree 来源由输入文件自证，未绑定受信任的前置 WORK 交付登记；任意提交可自标为允许前置 WORK 并通过。
3. **WORK→MODPLAN 工件哈希错误。** WORK 总方案声称随包 MODPLAN ZIP 为 `cee75c…`，实物为 `950dcf…`。这会破坏四级文档间的不可抵赖版本绑定，且现有版本脚本漏检。
4. **组织授权仍明确缺失。** 当前受控状态为 `DRAFT/PENDING_ORGANIZATIONAL_APPROVAL/BLOCKED`，授权文件明确禁止自标 `APPROVED_FOR_CONSTRUCTION`。
5. **代码、真实 DEV/UAT 与 Gate 均未关闭。** REPORT v1.5 的 13 项代码问题仍为 `REJECTED`；真实 WORK commit/patch、部署/回滚工件、DEV/UAT 证据尚未生成；DEC-013 与 Gate C 均为 `OPEN`。

上述前三项均不是“极个别微观文字瑕疵”：前两项会产生机器错误阳性，第三项使施工文档无法证明绑定的是当前上游工件。因此 `APPROVED WITH CONDITIONS` 也不适用。

### 5.2 `trunc_div_zero` 与 `Common/PvAmount.py` 设计复现

WORK-01 的实际设计函数为：

```python
def trunc_div_zero(numerator: int, denominator: int) -> int:
    if denominator == 0:
        raise ZeroDivisionError("denominator must not be zero")
    quotient = abs(numerator) // abs(denominator)
    return -quotient if (numerator < 0) ^ (denominator < 0) else quotient
```

最小复现：

```text
3/2=1
3/-2=-1
-3/2=-1
-3/-2=1
1/-2=0
-1/2=0
0/-2=0
1/0=ZeroDivisionError
```

四象限与零附近均为向零截断，算法裁为 `CONFIRMED`（设计级）。同一设计片段还实测：`"30.00"→30000000`、`"-100.25"→-100250000`；float、bool、int64 越界分别触发 `TypeError/TypeError/OverflowError`。

设计细节仍有一个非阻断健壮性缺口：`parse_db_amount_to_units(Decimal("NaN"/"Infinity"))` 通过 `value.as_tuple().exponent` 的内部运算偶然抛出非领域化 `TypeError`，没有显式 `value.is_finite()` 判定。它确实拒绝非有限值，但错误合同不够明确；见 `S6-06`。固定基线没有该文件，不能写成生产代码缺陷或已修复。
