`validate_work_patch.sh` 与 `validate_work_dev.sh` 均接受调用方参数 `--approved-registry FILE`，仅把该文件的 SHA 回写证据，没有把路径/摘要锚定到发布包的受信根。独立合成历史中：

### 5.4 依赖拓扑与回滚安全

从 `WORK_SCOPE_ALLOWLIST.json` 的 prerequisite 与 WORK-08 stage B 前置集合构图，得到 10 个执行节点、20 条直接边；Kahn 检测覆盖全部节点，无环。一个合法拓扑序为：

```text
WORK-01 → WORK-07A → WORK-08(A) → WORK-02 → WORK-03 →
WORK-04 → WORK-05 → WORK-06 → WORK-07B → WORK-08(B)
```

依赖设计为 `CONFIRMED`。但是多 Wave 的 commit 身份仍受 S6-02 影响，故“拓扑无环”不等于“累积树可信”。

`ROLLBACK_MANIFEST_SPEC.md` 要求每个待部署 WORK 提交真实、签名并在隔离环境演练通过的 manifest，包含部署对象、前后镜像、精确 argv、状态快照、数据恢复/重放、执行/复核/批准人和日志。规范层数据面分工及 07B 红线合理，判为 `CONFIRMED`；当前未提供任何真实 deployment/release/unit 或已演练 manifest，故实际独立回滚能力为 `UNVERIFIABLE / BLOCKED_EXTERNAL_EVIDENCE`，不得宣称已安全可执行。

## 7. 后续代码施工与 UAT 准入步骤建议

1. **先停留在文档/控制修订阶段。** 在 B7-01～B7-04 关闭前，不生成真实 WORK commit，不启动正式编码施工。
2. **重建受信注册表闭环。** 固定 registry 的发布身份/摘要或签名；对每个 APPROVED 条目同时验证 commit/tree、直接 patch、scope 结果、parent provenance、批准记录及批准主体，并执行伪造注册表负例。
3. **重跑第七轮文档治理门禁。** 从干净解包副本执行根及内层 SHA、Traceability 正例与全部负例、AC 原文集合差、当前轮次/版本引用校验、无 `/tmp` 的统一和独立自测入口；任何非预期 0 退出均阻断。
4. **取得组织施工授权。** 明确批准人、角色、签名原文、批准时间、范围和允许 Wave；将批准记录作为 registry 的受信输入，而非由 provenance 自报。
5. **按无环 Wave 生成真实提交。** 每个 WORK 仅产生 `PARENT_COMMIT→WORK_COMMIT` 直接 patch；前置 WORK 只有在其真实 DEV 证据复核并登记 APPROVED 后才可进入后续 parent tree。
6. **执行 DEV 双门禁。** 对每个 WORK 运行 baseline preflight、parent provenance、patch/scope/apply/tree、changed-file `py_compile`、专属测试以及测试后零 diff/零 untracked/tree 不变；保存命令、退出码、日志和 SHA。
7. **补齐部署/数据回滚证据。** 对每个 WORK 形成真实签名 `ROLLBACK-MANIFEST-PVAM-v1` 实例并在隔离环境演练；07B 禁止默认恢复固定 MAXLEN，紧急例外必须满足双签及全部容量/告警/停止阈值。
8. **开启 UAT 前置。** 取得 DEC-013 环境/权限/版本/数据，提供 DEC-009 DBA/架构批准的最小 schema manifest，固定 Redis/Kafka/Dask/GPU/SQL_MODE/镜像/配置/数据摘要。

10. **独立关闭 Gate。** 只有真实代码复核、DEV/UAT、receipt/checkpoint/retention/recovery、发布与回滚证据均通过后，才可重评 REPORT 代码结论和 Gate C；文档治理批准本身不得关闭任何运行 Gate。
